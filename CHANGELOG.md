# Changelog

Material changes to `@ethosagent/cli` and its workspace packages. Release-versioned history lives in `docs/content/changelog.md`; this file tracks unreleased schema-governance changes that require a justification per CONTRIBUTING.md.

## Unreleased

### Fixed

- **The turn-end compaction gate counts tool schemas, like the pre-LLM gate.** `maybeConsolidateAtTurnEnd` estimated usage from the system prompt and messages only, while a measured static slice (system + tools) sat in its threshold; with nothing measured it compared against `pressure × window` with the prefix counted as messages. A session with large tool schemas therefore compacted (and memory-flushed) late at turn end. `evaluateGate` in `packages/core/src/agent-loop/compaction.ts` now takes the serialized tool schemas (`CompactionDeps.toolSchemas`) and counts them in the usage estimate and in an unmeasured static slice, so `maybeCompact` and the turn-end trigger share one arithmetic instead of two; the turn end passes the definitions its LLM calls send (`turnToolDefinitions` over `TurnEndCtx.toolScope`). **Behavior change:** turn-end auto-compaction and the memory flush fire at the same whole-request threshold as the pre-LLM gate, i.e. once the messages outgrow `pressure × (window − static)`. The server-compaction skip and the verbatim tail are unchanged. Pinned by `packages/core/src/__tests__/turn-end-gate-units.test.ts`.

- **CLI and gateway sessions now measure the static prefix for compaction.** Context assembly derives the next turn's measured static slice (system prompt + tool schemas) from the newest assistant row's `usage.requestTokens` (Phase 1c, `stages/context-assembly.ts`), but `SQLiteSessionStore` never stored that field, so only the in-memory store ever measured: every CLI, gateway and web turn estimated the static slice with char/4, and on a dense local tokenizer the compaction gate and target were off by the difference. The split now lives in three nullable `INTEGER` columns on `messages` (`request_system_tokens`, `request_tools_tokens`, `request_messages_tokens`), added by `SQLiteSessionStore.migrate()` the same way as `trace_id` and `is_error`, and read back only when all three are set (NULL means "not measured", never zero). Rows written before the change read back unmeasured. **No `user_version` bump:** `sessions.db` stays at version 1, so rolling back with `ethos upgrade` to an older binary still opens the file (the `migrate()` guard in `packages/sqlite/src/migrate.ts` refuses only a newer version); the older binary ignores the extra columns and writes NULL into them. Pinned by `extensions/session-sqlite/src/__tests__/request-tokens.test.ts`, which includes an AgentLoop run on a real `sessions.db` whose turn-2 compaction target matches the in-memory store's.

- **Small-window mode, the tool-result budget and `/compact` follow each personality.** These were decided once, at startup, from the startup personality's static prefix in the startup directory. A `/personality` switch, a web or gateway turn for another personality, or a personality whose `fs_reach.workdir` holds a large `AGENTS.md` ran with the startup personality's answer. Each turn now asks a per-personality resolver (`createSmallWindowResolver`, `packages/wiring/src/small-window-resolver.ts`, through the optional `AgentLoopConfig.smallWindowResolver` seam applied by `setupTurn` and `withSmallWindow`, `packages/core/src/agent-loop/small-window.ts`). It measures that personality's SOUL, tool schemas, prelude and the project-context block its file-context injector renders in the workdir the turn resolves. From that floor it decides small-window mode and the window-scaled tool-result budget (`resolveResultBudgetGate`), honouring the personality's own `context_engine_options.resultBudgetChars`. The verdict is memoized per personality and workdir against a hash of the project context, so an unchanged `AGENTS.md` costs a stat per turn and a changed one is re-measured. A personality that newly engages small-window mode logs the same `small-window mode on` warning the startup personality does, once. Manual `/compact` on every surface (`AgentLoop.compact`) reads the history limit that personality's turns run with (`historyLimitFor`). The startup `small_window_toolset` log line now names the startup personality. Progressive sub-directory context layers are dynamic tail content and stay out of the static floor; `evaluateGate` counts them per turn with the whole prompt. **Behavior change:** under `compaction.smallWindow: on`, or on a window at or below 32k, each personality's first turn logs its own `small-window mode on` line. Not re-measured until restart: SOUL.md or toolset edits that leave the project context unchanged. Pinned by `packages/wiring/src/__tests__/small-window-resolver.test.ts` and `packages/core/src/__tests__/manual-compact-history-limit.test.ts`.

- **`ethos bench context` and the character sheet count the project context.** `ethos bench context` adds a `project ch` column, counted in `~tokens`, measured in the current directory or `--cwd <dir>` (or a personality's own `fs_reach.workdir`) through the same `FileContextInjector` class the loop uses (`createProjectContextInjector`, `packages/wiring/src/project-context-floor.ts`). `ethos personality show` and the web `personalities.characterSheet` RPC show the project-context contribution for a personality's declared workdir in `## Prompt size`, or say it depends on the working directory (`declaredWorkdirProjectContext`); `renderCharacterSheet` stays pure. The RPC gains an optional `promptSize` field, and the Personalities tab renders a Prompt size section from it. Pinned by `apps/ethos/src/__tests__/bench-context.test.ts`, `extensions/personalities/src/__tests__/character-sheet.test.ts`, `apps/web-api/src/__tests__/services/personalities.service.test.ts` and `apps/web/src/components/personality/__tests__/character-sheet-prompt-size.test.ts`.

- **Small-window mode counts the project-context injection.** `resolveSmallWindowMode` decided from the SOUL, the prelude and the tool schemas, but not the AGENTS.md/CLAUDE.md "Project Context" block, so with `provider: ollama` and a 32k window a static prefix at ~95% of the window stayed out of small-window mode when a ~78k-char AGENTS.md made up most of it. `buildAgentLoop` (`packages/wiring/src/build-agent-loop.ts`) now asks the loop's own file-context injector for the block the first turn will send, in the working directory the turn resolves (`projectContextAtStartup`, `packages/wiring/src/project-context-floor.ts`), and `measureStaticFloor` (`packages/wiring/src/static-floor.ts`) counts it as a `project context (AGENTS.md/CLAUDE.md)` component. The same floor feeds the startup fit warning and the local result-budget scaling. When small-window mode engages, startup now logs a warning naming the trigger, the prefix's share of the window and its largest part (`smallWindowModeMessage`). Per-personality measurement, `ethos bench context` and the character sheet: see the two entries above. Pinned by `packages/wiring/src/__tests__/small-window-project-context.test.ts`.

- **Compaction no longer drops all older history beside a large static prefix.** Every context engine (`drop_oldest`, `semantic_summary`, `reference_preserving`, `tiered_summary`, and the `templates/context-engine` starter) compares its own estimate of `currentSystem` plus `messages` against `targetTokens`, a whole-request budget. `maybeCompact` got the units wrong both ways. With a measured static slice it passed `0.7 × (window − static)`, a messages-only budget, and the engine subtracted the system prompt from it a second time. Without one it passed `0.7 × window` with the whole prefix counted as compactible — and that was every turn of a CLI or gateway session, because `SQLiteSessionStore` does not persist `usage.requestTokens`, so no stored turn ever carries a measured static slice. Either way, on a 32k window with a ~20k-token static prefix the target sat below the prefix, and `drop_oldest` dropped every older message even when most of them would fit. The target is now `compactionTarget` in `packages/core/src/agent-loop/compaction.ts`: the gate's own threshold at the target fraction (`gateThreshold(g, target)`, capped at the target fraction of `compaction.maxContextTokens`), minus the static tokens the engine cannot see (tool schemas), minus the current turn, so the engine's messages budget is exactly `target × (window − static)`. Context assembly passes the turn's serialized tool schemas (`CompactionDeps.toolSchemas`, the same definitions the LLM call sends, via `turnToolDefinitions` in `stages/stream-step.ts`); the pre-LLM gate counts them with the system prompt, and an unmeasured static slice is estimated from both, so measured and unmeasured turns get one target. **Behavior change:** the pre-LLM gate now counts the tool schemas in both the usage and the static slice, so on every turn it fires once the messages outgrow `pressure × (window − static)`. Before, a measured turn let the messages grow by the tool schemas' size past that, and an unmeasured turn fired at `pressure × window` with the prefix counted as messages. The turn-end gate (`turn-end.ts`) is unchanged. The `ContextEngine.targetTokens` doc comment (`packages/types/src/context-engine.ts`) now says what every engine already assumed; no interface change. Pinned by `packages/core/src/__tests__/compaction-target-units.test.ts`.

- **A turn is never sent without the user's message.** With `provider: ollama` and no `contextWindow`, the window resolves to the catalog value capped at 32,768 (`ARCH_WINDOW_CAP_TOKENS`, `packages/wiring/src/local-models.ts`). A ~27k-token static prefix (system prompt plus tool schemas) already sat above the pressure gate, so `maybeCompact` ran `drop_oldest` with a target the system prompt alone exceeded, and the engine dropped every message, the current question included. The provider received the system message alone and the model answered without the question. Compaction now hands a context engine only the history before the current turn (`currentTurnStart` in `packages/core/src/agent-loop/compaction.ts`, used by `maybeCompact` and the overflow retry's `emergencyCompact`), with the target reduced by the current turn's size, so no engine, built-in or third-party, can drop the question or split a tool round-trip. When the static prefix plus the question cannot fit the usable window (window minus output reserve), `streamStep` fails the turn before any request is sent, with an `error` event coded `context_window_too_small` and a `context_window_too_small` compaction event at severity `error` in observability. The message names `contextWindow`, `OLLAMA_CONTEXT_LENGTH`/`num_ctx`, `tool_loading: on` and `small_window_toolset` (`currentTurnFitError`, same file). **Behavior change:** a context engine's `compact()` no longer receives the current turn in `messages`, and its `targetTokens` excludes it. Pinned by `packages/core/src/__tests__/current-turn-protection.test.ts`. Not changed: the 32,768 fallback itself. Ethos already reads the served window from Ollama's `/api/ps` when the model is loaded, and it deliberately does not read `/api/show`, which reports the architecture maximum.

- **`ethos doctor` and `ethos gateway status` no longer migrate databases.** `checkSessionsDb` opened `sessions.db` through `SQLiteSessionStore`, the inbound-spool check and `gateway status` opened `inbound-spool.db` and `delivery-ledger.db` through their store classes, and `doctor --funnel` opened `observability.db` through the funnel tracker's wiring. Each constructor runs `migrate()`, so running a newer binary's diagnostics bumped `user_version` past what the older binary can open (`migrate()`'s downgrade guard, `packages/sqlite/src/migrate.ts`). Each surface now opens the file raw and reads it through handle-taking helpers the store classes also delegate to (`readSpoolStats` and friends in `@ethosagent/inbound-spool`, `readDeliveryStats` in `@ethosagent/delivery-ledger`, `readFunnelState` in `@ethosagent/wiring`). `ethos gateway spool replay|discard` writes the same way and refuses a spool at any schema version other than `INBOUND_SPOOL_SCHEMA_VERSION`. A newer-schema file is now read rather than reported as unopenable. Pinned by `apps/ethos/src/commands/__tests__/diagnostics-never-migrate.test.ts`, which also fails if `doctor.ts` or `gateway-status.ts` references any store class whose module migrates `user_version`. Not changed: `checkCodexModel` still lets `CodexTokenStore.load()` fold a legacy token file into the secret store, which is a secrets import, not a schema migration.

- **`/v1` CORS preflights use the `/v1` origin list.** The app-wide credentialed CORS middleware in `createRoutes` (`apps/web-api/src/routes/index.ts`) ran on every path, `/v1/*` included, and answered each preflight from `ETHOS_ALLOWED_ORIGINS` before `openAiCors` (`apps/web-api/src/middleware/openai-cors.ts`) saw it. Every `/v1` call carries `Authorization`, so it always preflights. A browser app listed in `ETHOS_API_CORS_ORIGINS` or `web.corsOrigins` therefore failed the preflight and could not call `/v1/*`, which the docs said it could. The app-wide middleware now skips `/v1/*`, and `openAiCors` owns that surface: preflights and responses answer from the `/v1` list, without credentials. Every other route is unchanged. **Behavior change:** an origin listed only in `ETHOS_ALLOWED_ORIGINS` no longer receives credentialed CORS headers on `/v1/*`; list it in `ETHOS_API_CORS_ORIGINS` if a browser app on it calls `/v1/*`. `/metrics` and `/cron/fire` keep the app-wide policy. Pinned by `apps/web-api/src/__tests__/routes/v1-cors-preflight.test.ts`.

### Security

- **WebSocket upgrades accept only a same-origin localhost port.** `originAllowed` (`apps/web-api/src/voice/voice-socket.ts`) gates the voice, satellite and browser-takeover sockets. It accepted any localhost / 127.0.0.1 / [::1] Origin on any port. An upgrade is a GET, so the CSRF middleware never sees it, and the `SameSite=Strict` auth cookie ignores port. A page on another local port could therefore open a cookie-authenticated mic, satellite or browser-takeover lane: the same hole L-d closed for HTTP. A loopback Origin now passes only when its host and port equal the upgrade's `Host` header. The comparison is `isSameOriginLocalhost`, moved to `apps/web-api/src/lib/same-origin.ts` so the CSRF check and the socket check share one copy. An upgrade with no Origin (a non-browser client such as a voice satellite daemon, which the cookie gates) and an origin listed in `ETHOS_ALLOWED_ORIGINS` pass as before. First-party clients are unaffected: the SPA opens these sockets on its own origin (`ethos serve`, `ethos boot`, the desktop shell). **Behavior change:** a browser page on another localhost port, or on `localhost` when the API was reached as `127.0.0.1`, can no longer open these sockets. A reverse proxy that rewrites `Host` must preserve it or list the origin in `ETHOS_ALLOWED_ORIGINS`. Pinned by `apps/web-api/src/voice/__tests__/voice-socket.test.ts`, `satellite-socket.test.ts` and `apps/web-api/src/browser/__tests__/takeover-socket.test.ts`.

- **The idle gateway's channel turns never get the unattended opt-in.** With no bot configured, `ethos gateway start` runs plugin channel turns (remote senders) on the systemLoop, which is also where cron, dreams, watcher wakes and call capture run. Its gate, `wireUnattendedApprovalGate` (`apps/ethos/src/unattended-approval-gate.ts`), honoured the D12 opt-in (`safety.approvalMode: off` + `allowUnattendedDangerousTools`) for every turn on that loop. So a stranger messaging the idle bot could run a flagged tool (`call`, `skills_pending_approve`/`reject`) that only trusted local work is meant to run unattended. The gate now takes a required `isRemoteSenderTurn(sessionId)`. `runGatewayStart` wires it to `Gateway.resolveApprovalRoute(sessionId) !== undefined`, a route `Gateway.runTurn` sets for its own channel turns only. A remote-sender call is judged by `createNoApprovalSurfaceGate`, the bot loops' gate: it is refused whatever the opt-in says, with the same no-surface text. Trusted local turns on the same loop keep the opt-in and the unattended text. If the origin test throws, the call is treated as remote. `ethos boot` needed no change: its idle bot shares the web loop, and that loop's approval predicate (`buildServeDangerPredicate`) never takes the opt-in. **Behavior change:** an idle-gateway personality on `approvalMode: off` with `allowUnattendedDangerousTools: true` now refuses flagged tools in channel chats. Its cron jobs still run them. Pinned by `apps/ethos/src/__tests__/unattended-approval-gate.test.ts` ('idle gateway', a real `Gateway` and `AgentLoop`) and `apps/ethos/src/commands/__tests__/gateway-unattended-gate-wiring.test.ts` (both hosts' wiring).

- **Bot loops with no approval card always refuse approval-flagged tools.** `wireApprovalFlow` (`apps/ethos/src/commands/gateway.ts`) registered its approval hook only on bots with an adapter that can post an approval card (Slack, Telegram, Discord), and returned early when there were none. So a WhatsApp, Email or webhook-route bot had no approval gate, and a flagged tool (`call`, `skills_pending_approve`/`reject`, and under `approvalMode: smart` anything the reviewer does not approve) ran with nobody asked. A turn that reached a card-capable bot's loop through a card-less adapter (an Email message falling back to a Slack bot) was let through by the hook too. Both now meet `createNoApprovalSurfaceGate` (`apps/ethos/src/unattended-approval-gate.ts`), which refuses the call with `<tool> needs approval, and this chat surface cannot show an approval prompt (<reason>). Use a platform with approval cards (Slack, Telegram, Discord) or the web UI.` `wireApprovalFlow` wires it for every bot loop it is handed, including the no-card early-return branch, so both hosts are covered by their existing call: `ethos gateway start`, and `ethos boot`'s `registerBotLive` (cold boot, live hot-add, webhook route bots, and a bot replaced on config reload). Each loop gets exactly one gate, the card flow or the no-surface gate. **There is no opt-in:** a remote sender drives these turns, so `safety.approvalMode: off` and `allowUnattendedDangerousTools` do not loosen this gate. The D12 pre-authorization stays systemLoop-only. **Behavior change:** a WhatsApp, Email or webhook-route bot that used to run a flagged tool now refuses it. Card-capable bots are unchanged for turns that arrive on their card-capable adapter. Pinned by `apps/ethos/src/commands/__tests__/approval-flow-unattended.test.ts`.

- **Web API CSRF check accepts only a same-origin localhost port (openclaw-advisory-fixes L-d).** The Origin check on state-changing `/rpc` and `/openapi` requests accepted any localhost / 127.0.0.1 / [::1] Origin on any port, so a page served from another local port (a dev server, a local tool) passed it. A localhost Origin now passes only when its host and port equal the request's `Host` header (`isSameOriginLocalhost`, `apps/web-api/src/middleware/csrf.ts`); `localhost` and `127.0.0.1` on the same port are different origins. `ETHOS_ALLOWED_ORIGINS` is unchanged and still replaces the localhost rule. First-party clients are unaffected: `ethos serve` and the desktop shell (local and remote mode, including its main-process RPC calls) are same-origin, and **the Vite dev server's API proxy entries now set `changeOrigin: false`** (`apps/web/vite.config.ts`). The plain-string entries they replaced meant `changeOrigin: true` in Vite, which rewrote `Host` to `:3000`. **Behavior change:** a local page on another port can no longer write through the API, and a reverse proxy in front of `ethos serve` that rewrites `Host` while the browser's Origin stays localhost must preserve `Host` or list the origin in `ETHOS_ALLOWED_ORIGINS`. Pinned by `apps/web-api/src/__tests__/middleware/csrf.test.ts` and `apps/web-api/src/__tests__/vite-proxy-origin.test.ts`.

- **Group-chat approvals are decided by the owner, not the requester (openclaw-advisory-fixes L-c).** The gateway's approval card was bound to whoever sent the triggering message, so in a group chat the member who asked for a dangerous call was the one person allowed to Allow it. `resolveApprovalTarget` (inside `wireApprovalFlow`, `apps/ethos/src/commands/gateway.ts`) now binds a group turn's approval to `channel_filter.<platform>.ownerUserId`; the requester's own click is dropped by `ApprovalCoordinator.settle`. DMs still bind to the requester. A group on a platform with no owner configured keeps requester binding (plan D21). `SessionRouting` gains `isDm` and `platform`, and `wireApprovalFlow` takes a required `ownerFor` seam, passed by both adapter-owning hosts (`ethos gateway start`, `ethos boot`). Pinned by `apps/ethos/src/commands/__tests__/approval-target.test.ts`.

- **Plugin contract: optional `SlashCommandContext.sender` (openclaw-advisory-fixes L-b).** A plugin slash command could not tell the bot owner from any group member, so every plugin command was effectively anyone-can-run. `SlashCommandContext` (`packages/types/src/plugin.ts`) gains one optional field, `sender?: { userId; isOwner; isDm }`. The gateway fills it in `Gateway.handleMessage`'s plugin branch — `isOwner` is `userId === channel_filter.<platform>.ownerUserId` (false when no owner is configured), `isDm` is the inbound message's — and the local CLI surfaces (`chat.ts` readline and `makeTuiSlashCommands`) pass `CLI_SLASH_SENDER`, `{ userId: 'cli', isOwner: true, isDm: true }`. **Contract class:** additive optional field on the Plugin contract (ARCHITECTURE.md §VII roster); per `packages/plugin-contract/src/version.ts` only a rename, a removal or a required field bumps `PLUGIN_CONTRACT_MAJOR`, so it stays at 4. **Obligation on plugin authors:** none to keep loading; a handler that gates on the owner must treat an absent `sender` (older host) as not the owner. Pinned by `extensions/gateway/src/__tests__/plugin-slash.test.ts` and `apps/ethos/src/__tests__/tui-capabilities.test.ts`.

- **Group `/personality` switches are owner-only (openclaw-advisory-fixes L-a).** On a bot with `allowSlashSwitch`, any member of a group chat could switch the whole lane to another personality. A group switch now requires `channel_filter.<platform>.ownerUserId`; a group on a platform with no owner configured refuses with a pointer to that key. DMs and the read-only forms (`/personality`, `/personality list`, `/personality rich`) are unchanged. Pinned by `extensions/gateway/src/__tests__/personality-switch-owner.test.ts`.

- **Personality deny rules now deny (openclaw-advisory-fixes Item 2).** `safety.denyRules` was documented as denying a matching call outright, but the wiring danger predicate returned it as an ordinary "needs approval" reason: on a surface with an approver the requester could Allow the call their own personality config said to deny, and on loops with no approval hook (`ethos chat`, WhatsApp/Email bots, the gateway systemLoop) the call ran. The match now happens in core, inside `enforceBeforeToolCall` (`packages/core/src/agent-loop/stages/per-call-enforcement.ts`), before any `before_tool_call` hook fires — so no approval card is posted, no web allowlist grant applies, and nobody can Allow it. It runs on every `AgentLoop`, on both the LLM batch path and the script bridge, and re-checks when a hook rewrites the args. The realtime voice host's direct tool dispatch (`createRealtimeToolHost`, `extensions/tools-voice/src/realtime-host.ts`), which runs outside `AgentLoop.run()`, used to fire `before_tool_call` itself and so skipped the deny rules, the post-rewrite re-check, result redaction and the payload's `personalityId`; it now calls `enforceBeforeToolCall` with the speaking personality's deny rules and `personalityId`, and passes every result through `redactToolResultSecrets` with the loop's kit (`AgentLoop.resultRedaction`, wired in `apps/web-api/src/voice/realtime-control-deps.ts`). It also fires the personality's plugin `before_tool_call` handlers, as the batch path does. The personality is resolved by the loop's own rule (`AgentLoop.resolvePersonality`, sharing `resolvePersonality` in `packages/core/src/agent-loop/stages/turn-setup.ts` with every turn), so a talk session that names none acts as the default personality, deny rules included; if nothing resolves, the host refuses every dispatch. No production tool dispatches directly today (`REALTIME_SAFE_TOOLS` is empty; `agent_consult` runs a full loop turn), so this closes a latent bypass; pinned by `extensions/tools-voice/src/__tests__/realtime-host.test.ts` ("core enforcement"). **Behavior change:** a deny-rule match that used to surface an approval card now fails immediately everywhere; no config migration. Pinned by `packages/core/src/agent-loop/__tests__/deny-rule-gate.test.ts`.

- **The gateway systemLoop no longer runs approval-flagged tools unattended; new `allowUnattendedDangerousTools` config key (openclaw-advisory-fixes Item 3).** Cron jobs, dreams, watcher wakes, call capture and SIP-inbound turns run on the gateway's systemLoop, which the approval flow never covered — so a tool that needs approval on a bot loop ran with nobody asked, and the SIP far-end spoken-confirmation refusal `sip-inbound-dispatch.ts` described was attached nowhere. `ethos gateway start` now registers a fail-closed gate on the systemLoop (`wireUnattendedApprovalGate`, `apps/ethos/src/unattended-approval-gate.ts`, generalized from the MCP export's gate): a call the approval predicate flags is refused with `no human is present to approve <tool> (<reason>)`, and a far-end caller's consequential request is refused by the spoken-confirmation wrapper. **Behavior change:** a cron or dream job that calls a flagged tool (`call`, `skills_pending_approve`/`reject`, and under `approvalMode: smart` anything the reviewer does not approve) now fails loudly instead of running. At boot the gateway records one warn-level `audit.block` event (`unattended_gate_cron_exposure`) and prints a line for every personality whose cron jobs can reach such a tool. **To pre-authorize** a personality that must use a flagged tool unattended, set `safety.approvalMode: off` on it AND add `allowUnattendedDangerousTools: true` to `~/.ethos/config.yaml`; the key feeds the previously unwired `allowAutoApproveDangerousTools` seam on the systemLoop predicate only, and bot loops never honour it (bot loops with no approval card always refuse, see the entry above). Deny rules and hardline commands still refuse. `ethos serve` and `ethos boot` are unchanged: their cron shares the web loop, whose approval modal a human can answer. Pinned by `apps/ethos/src/__tests__/unattended-approval-gate.test.ts` and `apps/ethos/src/commands/__tests__/gateway-unattended-gate-wiring.test.ts`.

- **Email `From:` was trusted as an identity with no authentication check (plan openclaw-advisory-fixes Item 6).** The email adapter set `userId` straight from the parsed `From:` header, and built the session's `chatId` from it too. Anyone could put an existing user's address in `From:` and inherit that user's identity-map entry, memory scope, `channel_filter` owner status and approvals, and, under a matching subject, their conversation. `processMessage` in `extensions/platform-email/src/index.ts` now calls the new exported `resolveEmailSender`. A sender counts as verified only when the topmost `Authentication-Results` header (RFC 8601) from the configured authserv-id reports `dmarc=pass` for the `From:` domain, or an aligned `dkim=pass`. Every other outcome fails closed: the sender becomes `email-unverified:<sha256(lowercased address)>`, the text starts with a one-line `[unverified sender]` notice, and the lane is keyed on that id. Replies still go to `From:`. Pinned by `extensions/platform-email/src/__tests__/sender-auth.test.ts`.

  **Action required for email deployments: set the new `emailTrustedAuthservId` key in `~/.ethos/config.yaml`.** Its value is the first token of the `Authentication-Results` header on any mail the account received: open the raw source of a message and read the first word after `Authentication-Results:` (`mx.google.com` on Gmail). **Until the key is set, every sender is unverified**, so existing email correspondents lose identity continuity on upgrade. `ethos gateway start` and `ethos boot` announce this with one warn-level `email.sender_auth_unconfigured` observability event and a console line. `ethos setup` keeps the key across re-runs, and in `ethos boot` an edit to it replaces the email bot live.

- **Tool-result secrets are redacted before anything reads the result, in errors as well as values (openclaw-advisory-fixes Item 7).** Secret detection ran only on a successful result's `value`, and only after `tool_end`, `after_tool_call`, the tool span and memory telemetry had already read the raw result. A secret in an error message (a failed HTTP call echoing its request URL with an API key) was never redacted, and a secret in a success reached the CLI, web SSE, channel adapters, plugin hooks and observability before the LLM-bound copy was cleaned. `redactToolResultSecrets` (`packages/core/src/agent-loop/stages/result-redaction.ts`) now runs once per result, on `value` when `ok` and on `error` when not, immediately after the result resolves. `processTools` (`tool-processing.ts`) maps it over the whole batch where `execResults` resolves, ahead of the returnDirect early exit, so sibling `tool_end`s, `persistReturnDirect` and `done.text` see redacted text too. `ScriptToolBridge.dispatch` (`script-tool-bridge.ts`) calls it for `run_code` inner calls before the inner `tool_end` and the script see the result. `safety.injectionDefense.blockSecretResults: false` and the `secret_in_tool_result` safety event keep their meaning. **Behavior change:** surfaces, hooks, spans and the persisted `tool_result` now carry the redacted text instead of the raw secret. The same pass redacts every string leaf of a successful result's `ToolResult.structured` (plain objects and arrays are walked, other leaves pass through), so `tool_end.structured` and the `after_tool_call` payload are clean too; the redacted payload is a fresh copy, the tool's own object is not mutated, and a result whose secret appears in both `value` and `structured` still records ONE `secret_in_tool_result` event. A cyclic or more-than-64-deep `structured` subtree (`MAX_STRUCTURED_DEPTH`) is replaced by `[REDACTED:unscannable]` whatever `blockSecretResults` says, since it could not be scanned. **Known limitation:** object keys inside `structured` are not scanned. Pinned by `packages/core/src/agent-loop/stages/__tests__/tool-processing-redaction.test.ts`.

- **`session_list_by_date` is scoped to the calling personality (openclaw-advisory-fixes Item 8).** The tool called `listSessions` with no personality filter, so any personality with the `memory` toolset could list every other personality's session ids and titles. It now passes `personalityId: ctx.personalityId` (`extensions/tools-memory/src/index.ts`, the `session_list_by_date` execute), and a call with no personality context is refused with `input_invalid` instead of listed unfiltered. **Behavior change:** sessions with no personality binding (a NULL `personality_id`, stored before binding existed) no longer appear in the list, because they cannot be attributed to the caller. `session_search` was already scoped to the calling session. Pinned by `extensions/tools-memory/src/__tests__/session-list-scoping.test.ts`.

- **`safeFetch` pins each connection to the addresses it validated (openclaw-advisory-fixes Item 9).** `safeFetch` resolved and validated a hostname, then let `fetch` resolve it again at connect time, so a resolver flipping its answer on a short TTL could steer the socket to an address that was never checked (DNS rebinding). The module header documented the race. On the default path each hop now goes through `pinnedFetch` (`packages/safety/network/src/safe-fetch.ts`): undici's `fetch` with a per-request `Agent` whose `connect.lookup` returns only the addresses `validateUrl` accepted. The hostname still drives Host, SNI and certificate checks. Each redirect hop re-resolves and re-pins, and a host whose resolution failed has no validated address, so it fails to connect instead of falling back to the system resolver. `undici ^7.28.0` is a new direct dependency of `@ethosagent/safety-network`. **Limits:** an injected `fetchImpl` is not pinned (the one production caller that injects one is the vision input resolver's `ctx.fetchImpl` test seam), and `web_fetch` / `web_extract` do not go through `safeFetch` (they use `extensions/tools-web/src/ssrf.ts`), so they remain exposed to rebinding. Pinned by `packages/safety/network/src/__tests__/safe-fetch.test.ts` ("connection pinning").

- **The `cron` tool no longer reaches across personalities (openclaw-advisory-fixes Item 1).** Only `create` scoped to the caller: `get`, `read_run`, `update`, `pause`, `resume`, `run` and `remove` took a bare id and never compared the job's owner, and `list` returned every personality's jobs unless the caller chose to filter — so a personality with the `cron` toolset could read, pause, delete, rewrite, or force-run another personality's job, the last one on the systemLoop as that job's personality. All seven now go through one gate, `loadOwnedJob` in `extensions/tools-cron/src/index.ts`, which returns the same `Job not found: <id>` for another personality's job as for a nonexistent id (no existence oracle). `list` always shows only the caller's jobs; its `personalityId` argument is removed from the schema and ignored if sent. A call with no personality context is refused for every action with the error `create` already returned. `update`, `resume` and `run` join `pause` and `remove` in refusing `source: 'system'` jobs (operator config). **Behavior change:** an agent can no longer see or manage jobs created by another personality; the operator's `ethos cron` CLI and web-api cron routes call the scheduler directly and are unaffected. Pinned by `extensions/tools-cron/src/__tests__/ownership.test.ts`.

- **`scaffold_personality` can no longer overwrite a personality or mint tools its creator lacks (openclaw-advisory-fixes Item 4).** reach-and-containment already refused the caller's own id and any id with a `config.yaml` under `~/.ethos/personalities/`. Two gaps remained. Built-ins live in the personalities package's `data/` dir, not under `~/.ethos`, so scaffolding a built-in's id wrote a user directory that shadowed it; the tool now also refuses any id `personalityRegistry.get` resolves. And `toolset.yaml` could list any registered tool, so a personality holding the design toolset could create a sibling with `terminal` and switch to it; the new toolset must now be a subset of the calling personality's own `toolset` (D13), and a caller that cannot be resolved, or whose `toolset` is undefined (read by the registry as "every built-in tool"), is refused rather than treated as unbounded. MCP and plugin tools are not granted through `toolset.yaml` (they are gated by `mcp_servers`/`plugins`, which scaffold never writes), so the exact-name subset is the whole check. Every refusal runs before the first `storage.mkdir`. Enforcer: `scaffoldPersonalityTool` in `extensions/tools-personality-design/src/index.ts`, which now takes the `personalityRegistry` dep (`PersonalityDesignDeps`, passed through `compose.ts` by `packages/wiring/src/compose-tools.ts`). **Behavior change:** editing an existing personality is a human action only (web Personalities tab or the files on disk). The built-in `personality-architect` and `team-architect` hold only the design tools, so they can now scaffold only personalities whose toolset is drawn from those tools; widening what they can create means widening their own toolset. Known residual: two concurrent scaffolds of the same new id can both pass the existence check. Pinned by `extensions/tools-personality-design/src/__tests__/no-overwrite.test.ts`.

- **A stored web grant or lease can no longer approve a hardline command (openclaw-advisory-fixes Item 10).** The web profile registers no `createTerminalGuardHook`/`createProcessGuardHook` — it asks instead of blocking — so its approval hook is the only gate for a hardline command (e.g. `rm -rf /`). But `ApprovalsService.requestApproval` consulted the one-hour lease and the allowlist first, so a single **Allow for 1 hour** or **Any args** on `terminal` silently approved every later hardline command with nobody asked; and the danger predicate inspected only `terminal`, so a hardline `process_start` command was not flagged on the web at all. Now `hardlineReason` (`packages/wiring/src/danger-predicate.ts`) covers both tools and is the predicate's first branch; `createWebApi` injects it into the web approval hook as `isHardline`, which marks the request `hardline: true`; `requestApproval` skips both the lease and the allowlist for it; and `approve` stores nothing for it whatever scope arrives — including `lease-1h` — resolving it as `once` and recording `requestedScope` on the audit row. The wire `ApprovalRequest` gains a required `hardline: boolean`, and the approval modal offers only **Just this command** for one. A human can still approve one hardline call on the web, which is the web profile's design; what is gone is a stored answer approving it. This covers every host that serves the web API (`ethos serve`, `ethos boot`, the desktop app), since all build the hook through `createWebApi`. Pinned by `apps/web-api/src/__tests__/services/approvals-hardline.test.ts` and the `process_start` case in `packages/wiring/src/__tests__/danger-predicate.test.ts`.

- **Web "always allow" grants are now bound to one personality (openclaw-advisory-fixes Item 5).** The web approval allowlist (`<dataDir>/allowlist.json`) keyed entries on tool name and args only, and `ApprovalsService.requestApproval` consulted it with no personality in hand — so an **Any args** grant for `terminal`, given once to one personality, auto-allowed `terminal` for every other personality that later asked through the same `ethos serve`/desktop/`ethos boot` process, with no card. Each entry now records the `personalityId` of the call it approved, and `AllowlistRepository.matches(personalityId, toolName, args)` honours an entry only for that same personality. A request with no personality, or an entry with none, never matches (fail closed). **Behavior change:** grants saved before this release stay in `allowlist.json` as an audit record but match nothing, so each re-prompts once and the new grant carries its personality; the file still parses, so nothing is reset. Pinned by `apps/web-api/src/__tests__/services/approvals-scoping.test.ts`.

- **Credential values are no longer written to disk in plaintext — G-SEC said they never were, and it was false in seven writers (security-boundary REC-002).** `config.yaml`, `~/.ethos/keys.json`, `~/.ethos/mcp.json`, and the per-plugin credential files each held real credential material: provider and auxiliary-model API keys, platform tokens, Slack signing secrets, webhook secrets, rotation-pool keys, MCP stdio `env` values, and plugin credentials. G-SEC publishes `SecretsResolver` as the **sole** storage and retrieval path for credential material and says config *"may reference a secret by name, never by value"* — with ARCHITECTURE.md §V S9 quoted in the row as *"No exception path exists for this rule."* The read path already resolved `${secrets:…}` references; it was the **writers** that persisted literals. All four files now hold `${secrets:<ref>}` references only, with the values in the resolver, and the register's own *Verify it yourself* grep now comes back empty on an install where keys were configured through either the CLI or the web UI.

  **Migration is automatic and needs no operator action.** The first write after upgrade lifts whatever plaintext the file still carries into the vault — `writeConfig`, `writeKeys` and the web's `ConfigRepository` externalize on the way out, and values that are already references pass through untouched, so rewriting an externalized file is a no-op on the vault. The read path still accepts legacy plaintext, so an install that has not written yet keeps working. Plugin credentials are the exception to "on next write": they migrate on **first touch** — before a plugin is handed its api, and before `ethos plugin credentials` lists or writes — and the legacy plaintext file is **deleted** once the value is in the vault. A one-time migration rather than a permanent read-through fallback, because a fallback leaves the second retrieval path open forever, which is the shape G-SEC forbids. If the vault write succeeds but the plaintext delete fails, the migration throws with the path to remove by hand rather than leaving a credential nothing will ever look at again.

  **Internal API change — `writeConfig` and `writeKeys` now take a required `SecretsResolver`.** `writeConfig(storage, config, secrets)` and `writeKeys(storage, keys, secrets)` in `@ethosagent/config`, and `ConfigRepositoryOptions.secrets` in apps/web-api. Required rather than optional on purpose: an omittable control is not a guarantee, and a resolver a caller could silently skip is exactly how plaintext kept reaching disk. Both write paths then run the existing `validateNoPlaintextSecrets` as a fail-closed gate over what is about to be serialized — reused rather than re-implemented, so the write check and the boot check can never disagree about what counts as plaintext. These are not part of the published plugin contract; out-of-tree callers of `@ethosagent/config` must pass the resolver.

  **The plugin contract was NOT bumped.** `EthosPluginApi.hasSecret(key)` stays **synchronous**, answered from a key set primed when the plugin is activated plus every `setSecret` since. The consequence is a staleness window worth stating plainly: a credential written by **another** process — the `ethos plugin credentials --set` CLI, or a second daemon — after the plugin loaded reads `false` until the plugin reloads. `getSecret` is async and always authoritative; treat a `false` from `hasSecret` as *"not known to be set"*, not as proof of absence. Making it async would have been a contract major for a method whose callers are almost all doing a startup capability check, so the cost was taken as documented staleness instead.

  **File modes tightened.** WhatsApp device-credential directories are now `0700` — Baileys writes the pre-key and credential files itself, so the directory mode is the only lever, and the mode is re-applied on **every** open rather than only at creation, so installs that already have a `0755` directory on disk are repaired rather than left behind. Plugin credential metadata is `0600` with its directory `0700`, and `mcp.json` is `0600` — it carries the `headers` and `env` blocks for every configured server, credential-adjacent even now that the values live in the vault.

  **Supporting changes.** One shared ref-naming table (`secretRefForConfigKey` in `@ethosagent/config`) serves both config serializers, so a rewrite from the CLI or the web lands on the same ref instead of minting a second one and orphaning the first; refs are keyed by stable botKey rather than array position where one exists. `keys.json` refs are content-addressed as `rotation/<hash-of-value>` because `KeyProfile` has no id and `label` is optional and not unique — there is nothing else stable to key on, and hashing survives reordering and leaks nothing. `ethos keys remove`, `ethos fallback remove` / `clear`, and webhook deletion in web-api now delete their vault material rather than orphaning it, writing config **first** and deleting **second** — the reverse order leaves config pointing at material that is already gone whenever the write fails, so the worst case is vault litter instead of a broken install; content-addressed refs mean removal also checks that no surviving entry still points at the ref. Three duplicate `${secrets:…}` parsers (fallback, platforms repository, config service) were consolidated onto one `secretRefFromValue`, keeping the strictest of the three behaviours: the whole value must be exactly one reference, since callers use it to decide what to **delete** and a loose parse deletes material something else still needs.

- **`fs_reach` was lexical only — a symlink planted inside an allowed prefix resolved outside it (security-boundary G11).** The personality filesystem boundary judged paths with `normalize(resolve())`, which is a string operation, while a symlink is a filesystem fact. A link at `<allowed>/notes.md → ~/.ssh/id_rsa`, or a symlinked *parent* such as `<allowed>/data → /etc` behind an ordinary leaf, satisfied the `fs_reach` allowlist **and** the always-deny floor, because the floor's guarantee was only "this path string is not a sensitive path" — never "this read does not reach a sensitive file."

  **Fixed at both filesystem boundaries.** `ScopedFsImpl.checkReach` (`packages/core/src/scoped/scoped-fs.ts`) and `ScopedStorage.check` (`packages/storage-fs/src/scoped-storage.ts`) now walk every path segment below the matched prefix with `lstat`, and on finding a link **resolve and re-judge** — the allowlist and the deny floor are both re-applied to the link's actual target — rather than refusing any symlink outright, so ordinary operator layouts (`/var` → `/private/var` on macOS) keep working. Each hop re-walks from the prefix that now contains the path, bounded at 32 hops. The lexical layers are still judged first and with no filesystem access at all, so a path outside the reach is refused on its string form and never reaches an `lstat` — the boundary leaks no existence information about paths it does not govern. The two implementations are deliberately duplicated (core may not runtime-import `@ethosagent/storage-fs` under the new security-kernel layer) and each now carries a reciprocal "these must change together" pointer at the other.

  **This closes misdirection, not TOCTOU.** An attacker who can swap a path between the walk and the subsequent `open` still wins. Closing that half needs kernel-tied operations (`openat` + `O_NOFOLLOW`) or container-level remediation, and remains open.

  **The documentation was wrong for a release.** `docs/content/security/controls.md` published this defense as *Shipped* while the code did not implement it: the original per-tool `realpath()` calls were removed during a refactor that centralised normalisation at the boundary — correct for lexical traversal, silently dropping the symbolic case — and no test, validator, or reviewer prompt failed. Four security pages were corrected (`controls.md`, `overview.md`, `threat-model.md`, `security-fixes.md`), and the new architecture validator now ties every published claim to a `file:line` enforcement point in both directions so a control cannot outlive its code again.

- **`StrictHostKeyChecking=accept-new` claimed pinning it could not deliver when the known-hosts file was not writable (`extensions/execution-ssh`).** `accept-new` means *learn the key on first sight, refuse it if it ever changes*, and the second clause is bought entirely by the learned key being **persisted**. OpenSSH does not treat a failed write as an error: verified against 9.6p1 with a real sshd, an unwritable destination — a read-only file, a read-only directory, or a directory that does not exist — prints `Failed to add the host to the list of known hosts (…)`, **runs the remote command anyway, and exits 0**. Every later connection is then a first connection that accepts whatever key it is offered: silent MITM exposure, while `config.yaml` and the character sheet both say the host key is pinned.

  The existing check was **lexical** — it refused `none` and the null-device spellings, values that keep nothing by construction — and could not see any of this. `sshKnownHostsUnwritableError` adds a pre-flight writability probe that runs **before ssh is spawned**, on both the exec path and the availability probe (a probe connection under `accept-new` is itself a first connection that pins a key). The refusal names the path and the fix (`mkdir -p` / `chmod u+w`). Inferring the loss of pinning afterwards from a warning line was not an option: by the time the warning exists, the command has already run remotely, unpinned.

  **The unset case is resolved, not skipped** — it is the common configuration and the one most likely to be wrong in a container. With no `execution.ssh.knownHostsFile`, the probe resolves ssh's own default `~/.ssh/known_hosts` (a learned key goes to the **first** file listed; `known_hosts2` is a read-only fallback). Absence is never an error — `accept-new` creates the file, which is how an operator adopts a dedicated known-hosts path — so what is checked in that case is the directory, with one exception: `~/.ssh` is the one directory ssh makes for itself, so a missing `~/.ssh` defers to the home directory rather than refusing a fresh container for a directory ssh would have created. `strictHostKeys: yes` skips the probe entirely: nothing is learned, so nothing has to be persisted, and a deliberately read-only known-hosts file is a legitimate deployment. Paths carrying ssh's `%`-tokens or `${ENV}` expansions are declined rather than guessed at — refusing a target on a mis-resolved path would be worse than the gap.

  The probe is **not** duplicated into `packages/config` the way the lexical check is: that one refuses a value, which is as true at boot as it ever will be; this one reads the filesystem, which a `chmod`, a mount, or a container's first run can change under a process that is already up. It needs raw `node:fs` (`accessSync`) inside `extensions/`, added to the Law 7 roster in AGENTS.md and `apps/ethos/src/__tests__/no-raw-fs.test.ts` with the argument in full — `Storage` has no writability probe, `exists()` answers a different question, and the only way to ask `Storage` whether a write would succeed is to perform one, which would mean Ethos writing into the operator's known_hosts to find out whether ssh could.

- **An `ssh_config` `LocalCommand` could run on the Ethos host while the posture reported the command as remote (`extensions/execution-ssh`).** Validating the destination and inserting `--` defends the argv; it does nothing against options loaded from a file. A `Host`/`Match` block in the operator's `~/.ssh/config` matching the target could set `LocalCommand`, which ssh executes **on the Ethos host** with the user's shell after every successful connection. Every connection now passes `-o PermitLocalCommand=no`, which closes `LocalCommand` and the `!command` escape. A command-line `-o` is read before any config file and ssh keeps the first value it obtains for an option, so a `PermitLocalCommand yes` in the config cannot win — verified against OpenSSH 9.6p1: with a config file setting it to `yes`, `ssh -F cfg -o PermitLocalCommand=no -G` resolves `permitlocalcommand no`. See the *Known limitations* entry below for what remains reachable, and why `-F none` was rejected.

### Changed

- **`ethos upgrade` keeps a new version only if it passes `ethos doctor` (plan `openclaw-9.5-adoption` item 4, D25/D26).** In npm mode it now records the running binary's `ethos doctor --json` as a baseline, runs `ethos backup` (a failure aborts before anything is installed), installs the exact `@ethosagent/cli@<latest>`, then runs the NEW binary's doctor, resolved from `$(npm root -g)/@ethosagent/cli/<bin>` and spawned with `process.execPath` rather than looked up on `PATH`. It rolls back with `npm install -g @ethosagent/cli@<previous>` when the new doctor cannot run or prints no report, reports another version, fails a core SDK, `db.ok` or a store integrity check, or fails a check the baseline passed. Checks already failing in the baseline, a stale gateway or call-capture heartbeat, unreachable channels and orphaned inbound-spool rows are printed and never roll back. After a rollback the old binary's doctor must match the baseline; if it does not, or the rollback install fails, upgrade exits 1 with the archive path and the exact `ethos import <archive>` command. It never restores and never restarts a gateway: a live gateway gets a restart hint. `--no-rollback` keeps the new version and still prints the diff. The registry lookup honours `npm_config_registry`. Trigger mapping: `failedChecks` in `apps/ethos/src/commands/upgrade.ts`; pinned by `apps/ethos/src/commands/__tests__/upgrade.test.ts`. **Behavior change:** `ethos upgrade` now exits 1 when the new version fails its health gate, and installs a pinned version instead of `@latest`.

- **Nothing a learning path drafts goes live without a replay or a human (plan `trust-before-reach.md` Part 4, L-T6).** Seven paths used to change a skill or an Expression, each with its own gate and three of them with none: the live post-turn fork copied a proposal straight into the live skills dir when `evolve-config.json` `autoApprove` was on; nightly skills went live on one LLM PASS/FAIL reply (`judgeSkillCandidate`, now deleted), with an omitted validator defaulting to PASS; `--auto-approve` on `ethos eval` and `ethos evolve` was a bare `rename` into the live dir. Every one of them — the fork, the nightly skill and Expression drafters, `ethos personality evolve`, the web Living Soul editor, chat `skill_propose`, and the eval-driven evolver — now submits a candidate to the learning inbox (`~/.ethos/learning/candidates/`), and the three legacy skill queues plus B-T1's `learning/pending-expression/` are drained into it once, on the next nightly run or `ethos personality evolve`.

  **With `autoApprove` on, a live-fork skill candidate no longer goes live instantly.** It waits for the next replay, and auto-promotes only on a `pass` verdict. Replay runs in the nightly pass — a new `replay` step after `skills`, capped by `learningReplay.maxCandidatesPerRun` and skipped when `learningReplay.enabled` is false — and never on `agent_done`: a replay costs minutes and money, and the post-turn hook is the wrong place for either. **`nightlyPass.enabled` defaults to false** (`packages/wiring/src/system-jobs.ts`, the `nightly-pass` job), so on an install that has not turned it on, the candidate waits for `ethos learning replay <id>` or the inbox's Run replay. `--auto-approve` on `ethos eval --evolve` and `ethos evolve` still works, and now replays each candidate synchronously inside that command instead of renaming files.

  **For `evolution_approval_mode: auto` personalities, an unevaluated Expression draft no longer applies (L-D2).** The Personality Judge still decides whether to draft; it no longer decides whether to apply. The draft is a candidate like any other and goes live only on a `pass` replay. `user` mode is unchanged in effect — nothing applies without a human — but the approval moved: the nightly draft is a candidate, and `ethos personality evolve <id>` offers it from the inbox rather than from `pending-expression/<pid>.json`.

  **Auto-promotion needs all three of: a `pass` verdict, the auto resolver answering `auto`, and a destination only the replayed personality can see** (`replayAndResolve`, `extensions/learning-inbox/src/auto-promotion.ts`). The resolver is the one reader of the three knobs that used to be read by three different paths: for skills, `skill_evolution.promotion` > `evolution_approval_mode` > global `autoApprove`; for an Expression, `evolution_approval_mode` only. Every existing opt-in keeps working, with one consequence to check: **a skill with the default `skill_evolution.scope` (shared) always needs a human now**, however it is configured, because replay tested it on one personality and it would run on every capability-matched one. Set `scope: personality` for a skill you want promoted unattended.

  **The agent can no longer approve a skill (L-D13).** `skills_pending_approve` returns a refusal naming the two human paths — the web Learning page and `ethos learning approve <id>` — instead of promoting. The auto resolver is the one non-human promotion path; a model approving its own proposal in chat would be a second, and on CLI and TUI, where no approval prompt appears, it would promote with no human at all. `skills_pending_reject` and the read tools are unchanged, since rejecting only narrows.

  Removed with this change: `judgeSkillCandidate` (`apps/ethos/src/commands/nightly.ts`), `registerSkillEvolutionAutoTrigger` and `resetSkillEvolutionCooldowns` (`extensions/skill-evolver`, which had no caller outside their own tests), `ImprovementForkOptions.autoApprove` / `onSkillApplied` and `CreateAgentLoopResult.setOnSkillApplied`, and the B-T1 queue module `apps/ethos/src/commands/pending-expression.ts`.

- **Personalities in `user` mode stop receiving nightly Expression changes without approval.** `user` is the default when `evolution_approval_mode` is absent, and its contract in `packages/types/src/personality.ts` says an Expression change is *"applied only on explicit user approval"*. The nightly pass never checked it: `runNightlyPass` step 3 called `applyExpression` → `FilePersonalityRegistry.evolveExpression` with no mode check anywhere on the path, so whenever the pass ran — `nightlyPass.enabled: true` in `~/.ethos/config.yaml`, or a manual `ethos nightly` — every personality not explicitly set to `auto` got its SOUL.md rewritten unapproved.

  The draft now **queues** at `~/.ethos/learning/pending-expression/<pid>.json` and `ethos personality evolve <id>` offers it, with the same rationale-and-diff surface and the same `y/N` prompt an in-session draft has always had. `y` applies it through `evolveExpression`; either answer deletes the file. A draft is a rewrite of specific text rather than a patch, so one whose base Expression has moved since — a hand edit, an `ethos personality revert`, an `auto` apply — is discarded with a notice instead of being offered, and the next run drafts a fresh one. A newer draft replaces an older one; the nightly step logs `queued for approval` rather than `applied`.

  **`evolution_approval_mode: auto` is unchanged** and is no longer inert — it has been the live Judge-gated path since phase 3b, and both readers (`runPersonalityEvolve` and the nightly pass) now honour it. The schema is untouched: no field was added, only the doc comment, which now names the two enforcers. The queue is backed up as `state` (`learning` → `state` in `packages/wiring/src/backup/scopes.ts`) — a pending approval is the only copy of a decision nobody has made yet, and the evidence window it came from has rolled off by the time a restore happens.

- **Three SQLite stores now run `synchronous = NORMAL` — a deliberate durability trade, taken per store and not across the roster.** `extensions/channel-transcript-sqlite`, `extensions/observability-sqlite` and `extensions/session-cards` no longer fsync the WAL on every commit. Measured on this repo's write paths, that fsync was essentially the entire cost of a write: 4.7 ms/record against 0.07 ms for the channel transcript (71x), 5.09 ms against 0.06 ms per observability span (79x), 4.04 ms against 0.02 ms per card append (181x). The cost is per-**commit**, not per-row, so it was the same ~4.5 ms whatever the row held — which is why it dominated three paths that commit small rows often.

  **What is given up, stated exactly.** Per [sqlite.org](https://www.sqlite.org/pragma.html#pragma_synchronous), WAL mode with `synchronous = NORMAL` is *"safe from corruption"* and *"always consistent"*; what it drops is durability — *"a transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash."* Application crashes lose nothing, at any setting: the OS still holds the writes. So the new exposure is precise and bounded — **a power cut or kernel panic can drop the last few transactions in these three files.** The database cannot be corrupted by it; WAL frames are checksummed and a torn frame is discarded at recovery.

  **Why these three and not the others.** Each holds data that is observational or expendable and is written often enough for the fsync to matter. The channel transcript is lines other people said in a watched room, on a retention window with a prune cron, written inline on the gateway's synchronous inbound path where every millisecond stops the event loop for every bot. Observability is telemetry with an explicit retention window, committing many times per turn; the tail a power cut drops belongs to a turn that did not finish either. A session card is a rendering of a tool result, in a store already built to degrade one card at a time.

  **Every store that backs a guarantee stays at `FULL`, and is now pinned by a test so a later blanket change cannot sweep it silently.** `delivery-ledger` (an obligation written `pending` before the platform call is the mechanism that stops a reply being lost), `job-store` and `notify-queue` (often the only record that work is owed), `inbound-dedup` (losing a sighting means a platform retry is reprocessed — a second billed LLM turn answering an answered message), `call-log` (`ringing`/`live` rows are live state, not history), `packages/a2a`'s task store (idempotency surviving a restart is the point of it), `memory-vector` (`memory.db` is the source of truth for memory content, not an index over it), and all three handles on `sessions.db` — the session store, the context log and the api-key store, since `synchronous` is a **per-connection** setting. None of those write paths is hot: they commit a handful of rows around events that take seconds, so `FULL` costs them well under 1%.

  **No operator action, no migration, no config.** `synchronous` is a per-connection runtime setting, not a property of the file, so existing databases are unaffected and reverting simply restores the old behaviour on the next open. The setting deliberately does **not** live in the `packages/sqlite` shim: a shim-wide default would be exactly the blanket decision this change argues against. The full per-store table and its reasoning are in AGENTS.md under *SQLite durability posture*. One stale comment was corrected in passing — the channel transcript's note on `AUTOINCREMENT` measured its cost while the fsync was still hiding it; re-measured without one, the `sqlite_sequence` write costs 14µs, which is still the right call for a correctness-load-bearing choice but is no longer free.

A 400 on the edit retries once without it, records `audit.compaction` / `llm.server_compaction_rejected`, and lets local compaction run for the rest of the turn. Any provider the turn does not resolve to a marked entry gets the summary as plain assistant text with the encrypted half dropped (`flattenCompactionEnvelopes`): core flattens it in `toLLMMessages` unless the turn's provider is marked, and `ChainedProvider` flattens it again per hop for a failover in the middle of a call, so a plugin provider never receives the envelope's nonce or `encrypted_content` (pinned by the "envelope reaches only a marked provider" tests in `packages/core/src/__tests__/server-compaction.test.ts`). Default off: no behavior change without the key. Both config writers keep the two keys (pinned by `packages/config/src/__tests__/config-provider-chain.test.ts` and `apps/web-api/src/__tests__/repositories/config.repository.test.ts`); the core rules by `packages/core/src/__tests__/server-compaction.test.ts`, the wire bytes by `extensions/llm-anthropic/src/__tests__/server-compaction.test.ts`. The compaction row cannot be forged by model output: it is marked structurally (`toolName` `_provider_compaction` with the payload in `contentBlocks`, written only by `compactionStoredRow` from `streamStep`), and the in-memory envelope a provider sees carries a per-process nonce (`decodeCompactionEnvelope`); a reply that merely starts with the envelope text stays text (pinned by the "forged envelope" tests in `packages/core/src/__tests__/server-compaction.test.ts`). Its `content` is the readable marker `— context compacted by the provider —` plus the summary, which is what transcripts, exports, `ethos chat` resume and full-text search see; the encrypted payload is kept out of the FTS index (`extensions/session-sqlite/src/__tests__/compaction-row.test.ts`), and the web chat history shows the marker line only. **Known limitations:** a failover in the middle of a request is not visible to the loop, so local compaction for that case starts on the next turn; side calls that share the provider instance (the compression summarizer, the injection classifier) also send the edit, so a large one can trigger a server compaction whose block is discarded. A session forked in the web UI, over ACP or with `/fork` keeps the block: `forkSession` (`packages/core/src/session-fork.ts`) copies every stored field, `contentBlocks` included (pinned by the "preserves every StoredMessage field" case in `packages/core/src/__tests__/session-fork.test.ts`).

### Known limitations

- **Persistent browser profiles are safe for one Ethos process at a time, and the docs said otherwise.** `docs/content/building/reference/browser-tools.md` published the per-profile mutex as an unqualified guarantee — *"A profile directory can only be open once. When a second concurrent session for the same personality asks for it, it waits 15 seconds for the first to finish, then gives up and launches an ordinary ephemeral context instead."* That is true only **within one process**. `acquireProfileLock` in `extensions/tools-browser/src/sessions.ts` is a promise-chain mutex over a module-scope `Map<string, Promise<void>>` — in-memory, process-local — while `~/.ethos/browser-profiles/<personality-id>/` is shared state on disk.

  **What actually happens across processes.** A second Ethos process running the same personality (`ethos serve` beside `ethos gateway`, the desktop app beside a CLI chat) never sees the first process's lock, so it neither waits the 15 seconds nor takes the ephemeral fallback. It collides with Chromium's own single-instance lock on the user data directory, `launchPersistentContext` throws, and `launchBackend` releases the profile lock and **rethrows** — the persistent path has no ephemeral fallback on a launch error. The user-visible result is a failed `browse_url` / `browser_navigate`, not a warning on a working session. That is a loud failure and not silent corruption; no profile corruption has been observed or is claimed.

  **Interim guidance, shipped in the docs rather than in code:** run one Ethos process per personality profile, or set `browser.profiles.enabled: false` on the secondary. Recorded in `browser-tools.md` (`#profiles-one-process`) and in the `profiles.enabled` notes of `docs/content/using/reference/config-yaml.md`.

  **The fix is not in this pass.** A real fix replaces the process-local mutex with the cross-process advisory lock this repo already uses twice — an exclusive `wx`-flag sentinel file with stale-holder detection, as in `extensions/agent-mesh/src/index.ts`'s registry lock and `packages/wiring/src/backup-schedule.ts`'s `backups/.lock`, both on AGENTS.md's sanctioned raw-`node:fs` roster. Until that lands, the guarantee is one process wide and the documentation now says so.

- **The `ssh` execution posture claims the *command* runs remotely, not that nothing runs locally — `ProxyCommand`, `ProxyJump` and `Match exec` still execute on the Ethos host.** They are loaded from the operator's `~/.ssh/config`, which no amount of argv hardening in `extensions/execution-ssh` can reach. `-o PermitLocalCommand=no` (see *Security* above) closes the gratuitous half — `LocalCommand`, which exists only to run something locally after connecting — and closes nothing else.

  **`-F none` was rejected as the fix.** It would close all of it by disabling the config file wholesale, and take `ProxyJump` and host aliases with it: reaching a target through a bastion is how a large share of real ssh deployments reach anything, so the "safe" version of the feature would be one its main audience cannot use. Trading a working feature for a boundary that was never claimed is the wrong trade.

  **This is trusted input, deliberately.** An operator's own ssh config on their own machine is not an attacker, and a config block matching the target is code they are choosing to run. The gap worth naming is the *posture claim*, not a privilege escalation: a reader of `ethos personality show` sees `ssh (remote host)` and should not read that as "no process starts on this machine." Documented for operators in `docs/content/using/how-to/run-tools-over-ssh.md` under *Read this before you enable it*. A tighter answer — allowlisting the resolved `ProxyCommand` against the operator's declared intent, via `ssh -G` — is not in this pass.
